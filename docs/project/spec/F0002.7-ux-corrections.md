# [CONCLUÍDO] Especificação: F0002.7 — Correções de UX (fidelidade ao `templates/referencia/`)

> Passe de **correção visual** entre a F0002.6 (onboarding minimalista) e as telas novas de
> Configurações/Pagamento (F0002.8). Alinha **todas as telas já implementadas** ao novo padrão:
> os protótipos [`templates/referencia/landing.html`](../../../templates/referencia/landing.html) e
> [`templates/referencia/dashboard.html`](../../../templates/referencia/dashboard.html) como **fonte da verdade visual** — ver
> [`docs/project/base/design-system.md`](../base/design-system.md). **Só aparência/UX**: NÃO altera modelo de
> dados, contratos de API nem regra de negócio (mesma natureza da F0002.5).

## Por que agora

A F0002.5 elevou a fundação de UX, mas as telas foram construídas **antes** de o `templates/referencia/`
existir como alvo concreto e de o **logo aprovado** ser fechado. Com o `templates/referencia/` agora definido
como fonte da verdade (docs/project/base/design-system.md), há divergências visuais acumuladas nas telas existentes. Corrigir
**antes** de construir as telas novas (F0002.8) evita propagar o padrão antigo e reduz retrabalho.

## Mudança de processo: prototipação obrigatória (retroativa a esta fase)

Duas rodadas de implementação direto em código (React/Next) foram reprovadas no gate de revisão
humana por falta de fidelidade visual — cada rodada custou um ciclo inteiro de código + testes +
deploy só para o usuário conseguir *ver* o resultado e dizer "não é isso". A partir de agora (ver
[P2S → prototipação da fronteira](../../p2s/principles.md)),
toda tela nova ou refeita passa por **protótipo HTML estático em `templates/prototipos/`**, iterado e
**aprovado explicitamente pelo usuário**, antes de qualquer código de produção.

**Isso se aplica retroativamente às 5 telas desta fase** — Login, Onboarding, Profissionais (lista +
form), App Shell, Dashboard — mesmo já tendo passado por 2 rodadas de código: cada uma será
reprototipada em `templates/prototipos/{slug}.html`, revisada tela a tela com o usuário, e só depois
de aprovada é que o código React existente é ajustado para bater com o protótipo aprovado (ou mantido,
se o usuário aprovar o que já está no ar). **F0002.8 não começa** até esse ciclo fechar para as 5
telas.

## O que mudou no padrão de UX (referência)

- **`templates/referencia/` é vinculante**: replicar `landing.html`/`dashboard.html` o mais fielmente possível —
  cores, tipografia, componentes, espaçamentos, radius e sombras (docs/project/base/design-system.md → "Referências visuais").
- **Dois moldes, não três**: **públicas** (marketing, **login**, **onboarding**) seguem o **Shell
  Público** (landing); **privadas** (pós-login) seguem o **App Shell** (dashboard).
- **Fim do Split Layout**: **remover** a "meia tela roxa" de login/onboarding (docs/project/base/design-system.md). **Login** vira
  **"Entrar com Google"** no topo do Shell Público (sem tela dedicada feia); **onboarding** vira
  **formulário centralizado** no Shell Público. Isso é mudança de **layout/UI** — continua **sem** tocar
  modelo, API ou regra de negócio.
- **Logo aprovado** (peso **bold**), variantes transparentes em `templates/referencia/assets/`:
  - Claro (`atendaz-logo.svg`): "Atend" `#111827` + "AZ" `#4F46E5`.
  - Escuro (`atendaz-logo-inverted.svg`): "Atend" branco + "AZ" `#93A0FA`.
  - Escolher a variante pelo **contraste com o fundo**; faixas escuras que hospedam o logo invertido
    usam `bg-primary` (`#4F46E5`), onde ele tem contraste.
- Identidade **confirmada**: primary indigo `#4F46E5` (não é mais "pendente").

## Escopo (telas-alvo — final, pós-prototipação)

1. **Home** (`/`) — substitui a antiga rota `/login`. Landing de marketing completa (hero, recursos,

Para **cada** tela: comparar lado a lado com o protótipo aprovado em `templates/prototipos/` (não mais
o `templates/referencia/` diretamente — esse é a referência que os protótipos seguiram). Divergência
só com motivo documentado (acessibilidade, restrição técnica), registrada aqui.

## Correções por tela (checklist de alinhamento)

> Itens são o alvo de fidelidade; a lista definitiva de divergências sai no `/p2s-plan` (auditoria
> tela a tela contra o `templates/referencia/`). Aqui ficam os pontos já conhecidos.

- **Global**
  - Substituir o logo antigo pelo **aprovado** (variante certa por fundo; `h-6`/`h-7`, `w-auto`).
  - Conferir tokens de cor/tipografia/espaçamento contra `templates/referencia/` (Inter, `tracking-tight`,
    pesos 600–800; fundo neutro `gray-50`, texto `gray-900`/muted `gray-500`).
  - Cards `rounded-2xl border border-gray-200 bg-white p-6 shadow-sm`; ícones lucide consistentes.
- **Home (`/`) — landing completa + modal de login**
  - Nav fixa (logo + Recursos/Como funciona/Preços + Entrar/Começar grátis), hero (headline, subcopy,
    trust bar, `AppMockupCard`), recursos (3 cards), como funciona (3 passos), preços (3 planos,
    conteúdo estático), CTA final (`bg-primary rounded-3xl`), footer.
  - **Sem rota `/login`**: "Entrar"/"Começar grátis"/CTAs de preço/CTA final abrem um **modal**
    (`HomeLanding.tsx`, estado local) ancorado `top-20 right-4/6`, sobre overlay leve
    (`bg-gray-900/10 backdrop-blur-[1px]`), com botão **X** de fechar + fecha no clique fora / `Esc`.
    Botão "Entrar com Google" **`bg-primary` + ícone branco** (não o G colorido — decisão explícita
    do usuário no gate).
- **Onboarding (Shell Público — 2 colunas, form em foco)**
  - `lg:grid-cols-5`: form `lg:col-span-3` (esquerda, card `rounded-2xl border shadow-sm`) + benefícios
    `lg:col-span-2` (direita: badge, headline, subcopy, 3 bullets ícone+texto — **sem** `AppMockupCard`
    aqui, pra não competir por atenção com o form).
  - Nav troca "Entrar" por **"Voltar"**, que desloga o usuário (`signOut({ callbackUrl: "/" })`) — sai
    do fluxo de criação de conta sem deixar sessão órfã.
- **App Shell**
  - Sidebar `~240px`, logo no topo (variante conforme o fundo da sidebar), **item ativo** com
    `bg-indigo-50` + texto/ícone `primary`; só **módulos ativos** aparecem (Guardrail 2 inalterado).
  - Topbar fina (nome fantasia + `/agendar/{slug}` muted + conta); mobile com **bottom tab bar**.
- **Profissionais**
  - Lista com `Table` (shadcn) dentro de card, toolbar (título/subtítulo + ações), cabeçalho
    `text-xs uppercase muted`, avatar de iniciais `bg-primary/10 text-primary`, `hover:bg-gray-50`.
  - Formulário: `Form` shadcn (RHF+Zod já existentes), inputs `h-10`, erro abaixo, máscaras/tooltips
    dos primitivos da F0002.5. **Envolto em card** (`rounded-2xl border bg-white shadow-sm`) e
    **centralizado** (`mx-auto`) dentro do conteúdo do App Shell — não grudado à esquerda. Campo do
    token do Asaas ganha **explicação sempre visível** (não só tooltip): o que é (Chave de API) e onde
    encontrar no painel do Asaas.
- **Dashboard**
  - Faixa de **cards de métrica** (ícone quadrado `bg-primary/10` + badge de tendência + número
    grande) como em `templates/referencia/dashboard.html`; card largo de gráfico + card lateral de composição.

## UX

### Fluxos
Nenhum fluxo novo. O **comportamento** (rotas, validações, navegação, gating de módulo, submit)
permanece **idêntico** ao já entregue — muda apenas a **apresentação**. Estados de tela
(loading/empty/error) e feedbacks (toast) continuam existindo, agora estilizados conforme `docs/project/base/design-system.md`.

### Telas
As telas seguem os **protótipos aprovados** em `templates/prototipos/` (fonte da verdade final desta
fase, construídos a partir dos padrões em `docs/project/base/design-system.md` e do `templates/referencia/`).
Referência-âncora por tela:

- **`/` (Home)** → `templates/prototipos/home.html`; `docs/project/base/design-system.md` › "Padrão: Home" (landing + modal).
- **`/onboarding`** → `templates/prototipos/onboarding.html`; `docs/project/base/design-system.md` › "Padrão: Onboarding".
- **Área autenticada** → `templates/prototipos/profissionais.html` / `dashboard.html`; `docs/project/base/design-system.md` ›
  "Padrão: App Shell" (sidebar/topbar/mobile).
- **Dashboard** → `templates/prototipos/dashboard.html`; `docs/project/base/design-system.md` › "Dashboard: cards de métrica / gráficos".
- **Profissionais** → `templates/prototipos/profissionais.html`; `docs/project/base/design-system.md` › "Tabela de dados (listas)" + Componentes Base (form em card).

## Guardrails

- **Proibido** tocar modelo (`docs/project/base/data-model.md`), rotas de API ou regra de negócio nesta fase.
- **Isolamento por `businessId`** e **module gating** (Guardrails 1 e 2) permanecem exatamente como
  estão — a correção é visual e não pode abrir/mudar dado exibido.
- **Sem regressão de contrato**: os testes de integração/API existentes devem continuar verdes sem
  alteração; só os testes de **render (RTL)** das telas tocadas são ajustados ao novo markup.

## Verificação

- **Local (Jest + RTL)**: a suíte existente passa sem mudança nos testes de API; os **testes de
  render** das telas tocadas (Login, Onboarding, Profissionais, App Shell, Dashboard) são atualizados
  para o novo layout e cobrem a superfície alterada (Política de Testes, `docs/p2s/quality.md` (Política de Testes)).
- **Stage/Prod**: abrir cada tela no Preview e **comparar lado a lado** com o protótipo `templates/referencia/`
  equivalente — logo correto por fundo, cores/tipografia/espaçamentos fiéis, componentes iguais.

## Critério de Aceite

- **Protótipo aprovado primeiro**: cada uma das 5 telas (Login, Onboarding, Profissionais, App Shell,
  Dashboard) tem um `templates/prototipos/{slug}.html` **aprovado explicitamente pelo usuário** antes
  de o código React correspondente ser considerado final.
- Login, Onboarding, Profissionais, App Shell e Dashboard ficam **visualmente fiéis ao protótipo
  aprovado** (que por sua vez segue o `templates/referencia/` como referência — logo na variante certa, cores,
  tipografia, componentes, espaçamentos), sem qualquer mudança de **comportamento, modelo ou API**.
- Nenhuma referência ao logo/identidade antigos permanece na UI.
- `npm test` verde, com os testes de render das telas tocadas refletindo o markup final aprovado.
