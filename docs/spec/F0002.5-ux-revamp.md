# Especificação: F0002.5 — Revamp de UX e Fundação de Componentes

> **Tipo:** fundação técnica + redesenho de apresentação. **Não** altera regras de
> negócio, modelo de dados, contratos de API nem Guardrails. É uma pausa estratégica
> entre F0002 (concluída) e F0003 para profissionalizar a UX e a base de componentes
> **antes** de construir as próximas telas (Perfil/Serviços, Agenda, Cobrança).

## Motivação

A interface atual ("feita à mão" com Tailwind puro) está pouco amigável e pouco
intuitiva, e cada nova feature recria os mesmos padrões de formulário/lista do zero —
violando DRY e acumulando dívida visual. Antes de F0003 em diante, vale investir em:

1. **Usabilidade**: mais texto explicativo (helper text, descrições, empty states,
   placeholders) em cada parte, para o usuário entender o que fazer sem tutorial.
2. **DRY**: componentes prontos e reusáveis em vez de reinventar a roda a cada tela.
3. **Performance e código limpo**: gestão de dados/cache padronizada no client.

## Decisões de Stack (fundação)

Adições à Golden Stack (todas **estáveis**, ver `README.md` e `docs/03`):

- **shadcn/ui** — biblioteca de componentes copiados para o repo (não é dependência
  versionada; gerada via CLI sobre **Radix UI** + `class-variance-authority` +
  `tailwind-merge` + `clsx`). Ícones via **lucide-react**. Evita reinventar
  Button/Input/Select/Dialog/Table/Form/Toast/Tabs/Card etc.
- **react-hook-form** + **@hookform/resolvers** (resolver **Zod**) — formulários
  performáticos e DRY; reusa os mesmos schemas Zod já usados na validação de API.
- **@tanstack/react-query** — fetching, cache, estados de loading/error e
  invalidação no client (substitui `useEffect`+`fetch` manuais).
- **@tanstack/react-table** — tabelas/listas (ordenação, paginação) headless,
  estilizadas com os componentes shadcn.

Princípio: **shadcn = não inventar a roda**; **react-hook-form/Zod = formulários DRY**;
**TanStack = dados e listas com menos código e melhor performance**.

## Escopo

**Inclui** (refatoração das telas já em produção para a nova fundação):

- Setup do shadcn/ui (tokens do `docs/10` mapeados para as CSS variables do shadcn),
  react-hook-form + Zod resolver e TanStack Query (provider global) + Table.
- Migrar os formulários de **Login**, **Onboarding** (wizard) e **Profissionais**
  para react-hook-form + componentes shadcn, mantendo o **Split Layout** e o **App Shell**
  já especificados em `docs/10`.
- Migrar listas/tabelas (ex.: lista de Profissionais) para TanStack Query + Table com
  estados completos (loading skeleton, empty com CTA, error com retry).
- Adicionar **copy explicativa** em cada tela: descrição do passo, helper text por
  campo, mensagens de empty state e textos de confirmação.

**Não inclui**: novas regras de negócio, novas rotas de API, novos módulos. Mudanças de
comportamento que não sejam apresentação devem ir antes para `docs/` (via `/ssd-doc`).

## UX

A fundação detalhada (tokens, Split Layout, App Shell, padrões globais de loading/
empty/error, validação inline) vive em **[`docs/10-design-system.md`](../10-design-system.md)**,
que esta fase **atualiza** para refletir shadcn/ui + react-hook-form + TanStack.

Diretrizes desta fase:

- **Mais texto, menos adivinhação**: todo formulário tem subtítulo de contexto; todo
  campo não óbvio tem `description`/helper text; toda lista vazia tem mensagem + CTA.
- **Consistência**: um único `Form`, `Button`, `Input`, `Select`, `Dialog`, `Table` e
  `Toast` (shadcn) usados em todo o app — sem variações ad-hoc.
- **Fidelidade ao que existe**: o redesenho **mantém** os layouts já especificados
  (Split Layout em `/login` e `/onboarding`; App Shell nas rotas internas); troca a
  implementação por componentes shadcn, não o padrão de tela.

## Decisões de UX adicionais (Fase 2.5)

Premissa: **o usuário é especialista no negócio dele, não no nosso vocabulário.** A
interface deve guiar sem exigir que ele entenda termos internos.

1. **Tooltips para jargão** — termos como **segmento**, **endereço público (slug)**,
   **Asaas**, **NFS-e** ganham ícone de ajuda (`ⓘ`) com explicação do que é e do que
   preencher. Padrão global em `docs/10`.
2. **Máscaras de input** — telefone/WhatsApp, CPF, CNPJ, CEP e valores em R$ usam
   máscara de preenchimento (persistir normalizado). Padrão global em `docs/10`.
3. **Tipo de pessoa (PF/PJ)** — **nunca** um campo único para CPF/CNPJ; um **switch**
   "Pessoa Física / Pessoa Jurídica" decide o tipo e troca máscara/validação do
   documento. Padrão global em `docs/10`.
4. **Biblioteca de ícones padrão** — **lucide-react** em toda a interface (já na
   fundação desta fase).
5. **Onboarding minimalista** — o onboarding deixa de pedir plano e Asaas; vira apenas
   **identidade**, para o usuário começar a usar o quanto antes (trial com sistema
   completo). Detalhes e telas na spec revisada **[`F0001-onboarding.md`](F0001-onboarding.md)**.
6. **Escolha de plano = quadro comparativo** — fora do onboarding, no painel (conversão
   pós-trial). Planos **lado a lado**, funcionalidades em linhas com ✓/—, nomes de
   módulo em **MAIÚSCULO** e **AGENDA** separada de **AGENDA PÚBLICA**. Detalhes na spec
   **[`F0011-platform-subscription.md`](F0011-platform-subscription.md)**.

## Verificação

- **Local (Jest)**: a suíte existente (rotas/API) continua **verde** — a refatoração é
  de apresentação e não deve quebrar contratos.
- **Stage/Prod (Cypress)**: smokes públicos de F0000/F0001/F0002 seguem verdes
  (status/redirect/401 inalterados). Fluxos autenticados validados manualmente no gate
  de revisão humana.
- **Guardrails**: gating de módulos, isolamento por `businessId` e resolução de billing
  permanecem intactos (nenhuma mudança de backend nesta fase).
