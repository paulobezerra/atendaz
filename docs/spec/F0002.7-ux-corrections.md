# Especificação: F0002.7 — Correções de UX (fidelidade ao `TEMPLATE/`)

> Passe de **correção visual** entre a F0002.6 (onboarding minimalista) e as telas novas de
> Configurações/Pagamento (F0002.8). Alinha **todas as telas já implementadas** ao novo padrão:
> os protótipos [`TEMPLATE/landing.html`](../../TEMPLATE/landing.html) e
> [`TEMPLATE/dashboard.html`](../../TEMPLATE/dashboard.html) como **fonte da verdade visual** — ver
> [`docs/10-design-system.md`](../10-design-system.md). **Só aparência/UX**: NÃO altera modelo de
> dados, contratos de API nem regra de negócio (mesma natureza da F0002.5).

## Por que agora

A F0002.5 elevou a fundação de UX, mas as telas foram construídas **antes** de o `TEMPLATE/`
existir como alvo concreto e de o **logo aprovado** ser fechado. Com o `TEMPLATE/` agora definido
como fonte da verdade (docs/10), há divergências visuais acumuladas nas telas existentes. Corrigir
**antes** de construir as telas novas (F0002.8) evita propagar o padrão antigo e reduz retrabalho.

## O que mudou no padrão de UX (referência)

- **`TEMPLATE/` é vinculante**: replicar `landing.html`/`dashboard.html` o mais fielmente possível —
  cores, tipografia, componentes, espaçamentos, radius e sombras (docs/10 → "Referências visuais").
- **Dois moldes, não três**: **públicas** (marketing, **login**, **onboarding**) seguem o **Shell
  Público** (landing); **privadas** (pós-login) seguem o **App Shell** (dashboard).
- **Fim do Split Layout**: **remover** a "meia tela roxa" de login/onboarding (docs/10). **Login** vira
  **"Entrar com Google"** no topo do Shell Público (sem tela dedicada feia); **onboarding** vira
  **formulário centralizado** no Shell Público. Isso é mudança de **layout/UI** — continua **sem** tocar
  modelo, API ou regra de negócio.
- **Logo aprovado** (peso **bold**), variantes transparentes em `TEMPLATE/assets/`:
  - Claro (`atendaz-logo.svg`): "Atend" `#111827` + "AZ" `#4F46E5`.
  - Escuro (`atendaz-logo-inverted.svg`): "Atend" branco + "AZ" `#93A0FA`.
  - Escolher a variante pelo **contraste com o fundo**; faixas escuras que hospedam o logo invertido
    usam `bg-primary` (`#4F46E5`), onde ele tem contraste.
- Identidade **confirmada**: primary indigo `#4F46E5` (não é mais "pendente").

## Escopo (telas-alvo — tudo que já foi implementado)

1. **Login** (`/login`) — **remover o split**; acesso "Entrar com Google" no **Shell Público**.
2. **Onboarding** (`/onboarding`) — passo único (identidade), **formulário centralizado** no Shell Público.
3. **Profissionais** — lista (tabela) + formulário (criar/editar), incluindo billing override.
4. **App Shell** — sidebar, topbar, navegação mobile (bottom tab bar).
5. **Dashboard / Visão Geral** — cards de métrica, gráficos (placeholder) e tabelas.

Para **cada** tela: comparar lado a lado com o protótipo/equivalente em `TEMPLATE/` e com os padrões
de `docs/10`, e replicar classes/tokens. Divergência só com motivo documentado (acessibilidade,
restrição técnica), registrada aqui.

## Fora de escopo

- Qualquer mudança de **modelo, rota de API ou regra de negócio** (isso é o que torna esta fase
  segura — igual à F0002.5).
- Telas ainda **não** construídas (Configurações/Pagamento → F0002.8; Serviços/Agenda → F0003+).
- Novas variáveis de ambiente (**nenhuma**).

## Correções por tela (checklist de alinhamento)

> Itens são o alvo de fidelidade; a lista definitiva de divergências sai no `/ssd-plan` (auditoria
> tela a tela contra o `TEMPLATE/`). Aqui ficam os pontos já conhecidos.

- **Global**
  - Substituir o logo antigo pelo **aprovado** (variante certa por fundo; `h-6`/`h-7`, `w-auto`).
  - Conferir tokens de cor/tipografia/espaçamento contra `TEMPLATE/` (Inter, `tracking-tight`,
    pesos 600–800; fundo neutro `gray-50`, texto `gray-900`/muted `gray-500`).
  - Cards `rounded-2xl border border-gray-200 bg-white p-6 shadow-sm`; ícones lucide consistentes.
- **Login / Onboarding (Shell Público — sem split; hero de 2 colunas)**
  - **Remover** o painel roxo full-height e a estrutura 50/50 de ambas as rotas.
  - Envolver as duas na moldura do Shell Público (nav com **logo claro** + ações padrão "Entrar"/
    "Começar grátis"; fundo branco; `max-w-6xl`).
  - **Login**: reaproveita o **hero da landing** (headline, subcopy, trust bar) como pano de fundo —
    ainda não existe landing de marketing (F0012), então `/login` funciona como porta de entrada
    pública. 2 colunas (`lg:grid-cols-2`): hero à esquerda, **card de acesso** ("Entrar com Google") à
    direita, no lugar do mockup do app que a landing completa usaria.
  - **Onboarding**: 2 colunas — `AppMockupCard` + benefícios à esquerda, **card do form** (`max-w-lg`)
    à direita; botão primary `full-width`; sem stepper lateral. (Revisão de gate: a versão anterior,
    card único centralizado, foi reprovada por "tudo branco" — ver `docs/10` para o padrão atual.)
- **App Shell**
  - Sidebar `~240px`, logo no topo (variante conforme o fundo da sidebar), **item ativo** com
    `bg-indigo-50` + texto/ícone `primary`; só **módulos ativos** aparecem (Guardrail 2 inalterado).
  - Topbar fina (nome fantasia + `/agendar/{slug}` muted + conta); mobile com **bottom tab bar**.
- **Profissionais**
  - Lista com `Table` (shadcn) dentro de card, toolbar (título/subtítulo + ações), cabeçalho
    `text-xs uppercase muted`, avatar de iniciais `bg-primary/10 text-primary`, `hover:bg-gray-50`.
  - Formulário: `Form` shadcn (RHF+Zod já existentes), inputs `h-10`, erro abaixo, máscaras/tooltips
    dos primitivos da F0002.5. **Envolto em card** (`rounded-2xl border bg-white shadow-sm`) e
    **centralizado** (`mx-auto`) dentro do conteúdo do App Shell — não grudado à esquerda. Campo do
    token do Asaas ganha **explicação sempre visível** (não só tooltip): o que é (Chave de API) e onde
    encontrar no painel do Asaas.
- **Dashboard**
  - Faixa de **cards de métrica** (ícone quadrado `bg-primary/10` + badge de tendência + número
    grande) como em `TEMPLATE/dashboard.html`; card largo de gráfico + card lateral de composição.

## UX

### Fluxos
Nenhum fluxo novo. O **comportamento** (rotas, validações, navegação, gating de módulo, submit)
permanece **idêntico** ao já entregue — muda apenas a **apresentação**. Estados de tela
(loading/empty/error) e feedbacks (toast) continuam existindo, agora estilizados conforme `docs/10`.

### Telas
As telas seguem os **padrões já desenhados** em `docs/10-design-system.md` (Shell Público, App Shell,
Dashboard: cards/gráficos/tabela) e os protótipos em `TEMPLATE/`. Para login/onboarding esta fase
**troca o layout** (split → Shell Público); nas demais, faz a implementação existente **casar** com os
desenhos. Referência-âncora por tela:

- **`/login` e `/onboarding`** → `docs/10` › "Padrão: Shell Público" (login = botão Google; onboarding = card centralizado).
- **Área autenticada** → `docs/10` › "Padrão: App Shell" (sidebar/topbar/mobile).
- **Dashboard** → `docs/10` › "Dashboard: cards de métrica / gráficos" + `TEMPLATE/dashboard.html`.
- **Profissionais** → `docs/10` › "Tabela de dados (listas)" + Componentes Base (form em card).

## Guardrails

- **Proibido** tocar modelo (`docs/04`), rotas de API ou regra de negócio nesta fase.
- **Isolamento por `businessId`** e **module gating** (Guardrails 1 e 2) permanecem exatamente como
  estão — a correção é visual e não pode abrir/mudar dado exibido.
- **Sem regressão de contrato**: os testes de integração/API existentes devem continuar verdes sem
  alteração; só os testes de **render (RTL)** das telas tocadas são ajustados ao novo markup.

## Verificação

- **Local (Jest + RTL)**: a suíte existente passa sem mudança nos testes de API; os **testes de
  render** das telas tocadas (Login, Onboarding, Profissionais, App Shell, Dashboard) são atualizados
  para o novo layout e cobrem a superfície alterada (Política de Testes, `docs/07` §4.1).
- **Stage/Prod**: abrir cada tela no Preview e **comparar lado a lado** com o protótipo `TEMPLATE/`
  equivalente — logo correto por fundo, cores/tipografia/espaçamentos fiéis, componentes iguais.

## Critério de Aceite

- Login, Onboarding, Profissionais, App Shell e Dashboard ficam **visualmente fiéis ao `TEMPLATE/`**
  (logo aprovado na variante certa, cores, tipografia, componentes, espaçamentos), sem qualquer
  mudança de **comportamento, modelo ou API**.
- Nenhuma referência ao logo/identidade antigos permanece na UI.
- `npm test` verde, com os testes de render das telas tocadas refletindo o novo markup.
